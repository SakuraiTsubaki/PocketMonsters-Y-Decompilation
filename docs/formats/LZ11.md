# Nintendo LZ11 compression (`0x11`)

## Status

**Public-implementation baseline; not yet verified against a local Pokémon Y dump.**

Project Shutan identifies LZ11 as a compression format used by Gen VI resources. Its page is incomplete, so this document cross-checks the format against the public pk3DS implementation rather than treating the wiki TODO as a full specification.

## Container signature and decompressed length

A public Gen VI implementation accepts a stream as LZ11 when its first byte is `0x11`.

The initial header is interpreted as:

```text
byte 0      0x11
bytes 1..3  decompressed size (24-bit Nintendo/DS-style value)
```

If the 24-bit decompressed size is zero, pk3DS reads the following four bytes as an extended decompressed length.

## Block stream

After the length header, data is processed in groups controlled by one flag byte.

- one flag byte describes the next eight blocks;
- flag bits are consumed MSB first;
- flag bit `0` means one literal byte follows;
- flag bit `1` means a back-reference follows.

The decompressor maintains a `0x1000`-byte history window. Displacement is encoded as a 12-bit value plus one, giving an effective maximum backward distance of `0x1000` bytes.

## Back-reference encodings

The high nibble of the first encoded byte selects one of three length encodings.

### Indicator greater than 1

Two encoded bytes are consumed.

```text
length = high_nibble + 1
disp   = 12-bit displacement + 1
```

### Indicator equal to 0

Three encoded bytes are consumed.

```text
length = encoded_length + 0x11
disp   = 12-bit displacement + 1
```

### Indicator equal to 1

Four encoded bytes are consumed.

```text
length = encoded_length + 0x111
disp   = 12-bit displacement + 1
```

A decoder must reject a reference that reaches farther backward than the amount of data already produced.

## Padding

The pk3DS implementation tolerates trailing alignment bytes after the compressed stream and explicitly comments that input may be four-byte aligned. Padding must therefore be preserved or handled deliberately rather than silently treated as compressed content.

## Relationship to GARC

Project Shutan leaves open whether compression is selected at GARC level or per individual file. pk3DS provides stronger implementation evidence for at least one important case: during GARC extraction it inspects each extracted member's first byte for `0x11` and optionally decompresses that member.

Therefore this project records:

- **observed public implementation:** LZ11 can be applied to individual GARC members;
- **not yet proven here:** that every Gen VI LZ11 use is exclusively per-member or that whole-container use never occurs.

## Tooling requirements

A clean-room project implementation should eventually provide:

- `is_lz11(data)` signature/header validation;
- lossless decompression;
- deterministic compression;
- strict bounds checks;
- preservation/reporting of trailing padding;
- synthetic fixtures covering literal blocks and all three back-reference forms;
- malformed-stream tests for short input, impossible displacement, and inconsistent output length.

ROM-derived fixtures must not be committed merely to obtain test coverage. Synthetic vectors are sufficient for the initial unit-test suite.
